SR500 / OpenClaw Project Overview

This page is a compact overview of the whole SR500 setup: the Raspberry Pi runtime, the GPS pipeline, the export and map repositories, the OpenClaw agents, and the logic that ties them together. It is meant to be a human-readable system map, not the source of truth for raw data or operational scripts.

The system has three main layers: data collection on the Pi, versioned export/publishing repositories, and OpenClaw agents that read and present the results.

1. Conceptual architecture

🏍️Motorcycle / GPS

The u-blox 7 device provides positions through gpsd. This is the physical source of the entire data flow.

↓

🍓Raspberry Pi “SR500”

/home/johnny/mc-gps/ runs logging, trip building, export generation, map rendering, sync, and database pruning.

↓

📦sr500exports

Repository-format trip data: latest.json, summaries, GeoJSON, and GPX. This is the main read surface for agents.

＋

🗺️sr500maps

Published HTML maps and index pages. This is the presentation layer for interactive trip maps.

↓

☁️GitHub / GitHub Pages

The Pi pushes both repositories. The map repository is served as a static site through GitHub Pages.

↓

🤖OpenClaw

The main agent and trip-map-agent read repository-format data, use memory and tools, and avoid direct Pi access for ordinary trip requests.

↓

💬Chat / Control UI

The user receives text, images, links, or HTML-derived views depending on the surface and the request.

The key idea is simple: the Pi does the collection, processing, and publishing; OpenClaw reads from stable repository and publishing surfaces and presents the result in chat or UI.

2. End-to-end flow

Step 1: The GPS device feeds positions into gpsd on the Pi.
Step 2: gps_logger.py stores valid GPS points in gps.db.
Step 3: trip_builder.py groups points into trips, splits trips at long gaps or long idle periods, and filters out drift-like noise.
Step 4: export_gps.py generates repository-readable files: latest.json, trip summaries, GeoJSON, and GPX.
Step 5: render_trip_html.py and render_maps_index.py build publishable HTML maps into sr500maps.
Step 6: sync_exports.sh and sync_maps.sh commit and push changes when files have actually changed.
Step 7: OpenClaw and trip-map-agent read the exported data and respond with lists, images, HTML, or published links.

4. Trip logic

Trips are not simply “all points in order”. The project uses configurable rules to decide what counts as a real trip, what counts as an idle break, and what looks like GPS drift.

  • A new trip starts when real movement resumes.
  • A trip can end after a data gap longer than 5 minutes.
  • A trip can also end after roughly 15 minutes of low movement inside a small radius.
  • Noise-like trips are filtered out when they look like drift: low distance, long duration, low average speed.

The main thresholds currently live in /home/johnny/mc-gps/config/trip-config.env:

TRIP_GAP_SECONDS=300
TRIP_IDLE_SECONDS=900
TRIP_IDLE_RADIUS_METERS=30
TRIP_RESUME_MOVE_METERS=50
MIN_REAL_TRIP_DISTANCE_KM=1.0
MIN_REAL_TRIP_AVG_SPEED_KMH=2.0
MIN_REAL_TRIP_DURATION_SECONDS=600

  • trips/trip-*.summary.json – trip metadata

sr500maps

The public map repository and GitHub Pages surface.

  • index.html – published trip index
  • latest.html – latest rendered trip
  • trips/trip-<trip_id>.html – per-trip map pages
  • project-overview.html – this overview page

6. Time handling

Raw timestamps are stored in UTC with a Z suffix in latest.json, summaries, GeoJSON, and GPX. That is intentional and keeps the stored data clean and consistent.

The human-facing map layer has been updated to display times in Europe/Oslo, so published HTML maps and the map index show local Norwegian time.

  • Storage: UTC
  • Presentation: Europe/Oslo (CET/CEST)

7. OpenClaw setup

OpenClaw runs locally with the gateway on the same machine as the main agent. The primary chat model is microsoft-foundry/gpt-5.4, and the trip-focused sub-agent uses the same model. Memory search was moved to local Ollama embeddings to keep recall local and more reliable.

Models

  • Primary model: microsoft-foundry/gpt-5.4
  • Configured agent models: microsoft-foundry/gpt-4o, microsoft-foundry/gpt-5.4
  • Embedding model: nomic-embed-text through Ollama

Memory

  • Provider: ollama
  • Model: nomic-embed-text

  • Tool profile: coding

Why the memory setup matters here: memory recall had become fragile enough that project context did not always come back when needed. The fix was to switch embeddings to local Ollama, pull nomic-embed-text, and reindex the main agent's memory. That restored local recall for facts about the Pi, repositories, services, and the SR500 architecture.

10. Why this architecture works

  • The Pi does the heavy operational work where the GPS hardware actually is.
  • The repositories act as clean, versioned, shareable interfaces.
  • OpenClaw agents can read history and state without depending on live SSH access for ordinary queries.
  • GitHub Pages provides a simple and robust publishing surface for interactive maps.
  • UTC in stored data plus local time in presentation gives both technical consistency and human-friendly output.

11. Current limitations

  • The trip logic is still heuristic and will continue to need tuning against real rides.
  • The export structure still uses a flat trips/ directory.
  • Some operational scripts still live in the Pi runtime environment rather than in a dedicated code repository.
  • The agent experience can still improve around clearer choice between image, link, HTML, and GPX delivery.

12. Summary

The system can be understood as one chain: GPS device → Pi runtime → SQLite → trip building → export repo → map repo → OpenClaw agents → chat/UI. Each layer has a clear role, and together they make the project operable, searchable, and easy to present.

This page lives in the map repository as practical architecture documentation, even though its scope is wider than maps alone.
