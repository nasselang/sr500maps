SR500 / OpenClaw prosjektoversikt

Dette dokumentet samler hele SR500-oppsettet i én lesbar HTML-side: Raspberry Pi-en, GPS-logikken, eksport- og kart-repoene, OpenClaw-agentene og hvordan delene henger sammen. Det er ment som en menneskelig systemoversikt – ikke som kilde for rådata eller driftsscript.

Prosjektet spenner over tre lag: innsamling på Pi, versjonerte eksport-/kartrepoer og OpenClaw-agenter som leser og presenterer resultatet.

2. Hovedidé

Motorsykkelen har ikke en chat-agent direkte koblet til seg hele tiden. I stedet samler Pi-en inn GPS-data, bygger turer, eksporterer dem til repo-format, og publiserer kart. OpenClaw leser deretter disse eksporterte, versjonerte artefaktene i stedet for å være avhengig av å SSH-e inn i runtime-miljøet for vanlige forespørsler.

Kjerneprinsipp: rå drift og logging skjer på Pi-en, mens OpenClaw-agentene helst leser fra stabile repo-/eksportflater. Det gir færre koblinger, mindre skjørhet og enklere deling.

3. Logikken bak hele flyten

Steg 1: GPS-donglen leverer posisjon via gpsd på Pi-en.
Steg 2: gps_logger.py skriver gyldige GPS-punkter til gps.db.
Steg 3: trip_builder.py grupperer punktene til turer, avslutter tur ved lange gap eller langvarig lite bevegelse, og filtrerer bort støy.
Steg 4: export_gps.py bygger repo-lesbare filer: latest.json, summary.json, geojson og gpx.
Steg 5: render_trip_html.py og render_maps_index.py bygger publiserbare HTML-kart til sr500maps.
Steg 6: sync_exports.sh og sync_maps.sh committer og pusher repoene når filer faktisk har endret seg.
Steg 7: OpenClaw og trip-map-agent leser repo-formatet og kan svare med liste, bilde, HTML eller lenke.

5. Turlogikken

Turene er ikke bare “alle punkter fortløpende”. Prosjektet bruker regler for å avgjøre hva som er en reell tur, hva som er pause, og hva som bare er støy. Både gps_logger.py og trip_builder.py bruker terskler fra trip-config.env.

  • Ny tur kan startes når faktisk bevegelse gjenopptas.
  • Tur kan avsluttes ved mer enn 5 minutters datagap.
  • Tur kan også avsluttes ved omtrent 15 minutters lite bevegelse innen liten radius.
  • Støy-turer filtreres bort dersom de ser ut som GPS-drift: lav distanse, lang varighet, lav snittfart.

Standard terskler inkluderer blant annet:

TRIP_GAP_SECONDS=300
TRIP_IDLE_SECONDS=900
TRIP_IDLE_RADIUS_METERS=30
TRIP_RESUME_MOVE_METERS=50
MIN_REAL_TRIP_DISTANCE_KM=1.0
MIN_REAL_TRIP_AVG_SPEED_KMH=2.0
MIN_REAL_TRIP_DURATION_SECONDS=600

6. Tidssoner og tidsvisning

Rådata lagres i UTC med Z-suffix, for eksempel i latest.json, summary.json, GeoJSON og GPX. Det er bevisst og teknisk ryddig.

Visningslaget er derimot nå oppdatert til å presentere tidene i norsk lokal tid (Europe/Oslo) i de publiserte HTML-kartene og kartindeksen. Det betyr i praksis:

  • Lagring: UTC
  • Presentasjon: norsk lokal tid (CET/CEST)

8. OpenClaw og agentene

OpenClaw er laget for å kunne lese prosjektet uten å være avhengig av driftstilstanden på Pi-en i hver eneste forespørsel. Derfor er sr500exports og sr500maps viktige som stabile mellomlag.

Hovedagenten

Har langtidsminne om prosjektet, kan gjøre operativ feilsøking, dokumentere beslutninger og hjelpe med vedlikehold.

trip-map-agent

Spesialisert agent for å lese sr500exports-formatet, finne historiske turer, resolve siste tur og rendre kart.

Primær datakilde er workspace-klonen av sr500exports, med fallback til andre lokale kilder eller synthetic testdata.

OpenClaw-konfig i dette oppsettet

OpenClaw kjører lokalt med gateway på samme maskin som hovedagenten. Hovedmodellen er satt til microsoft-foundry/gpt-5.4, og trip-map-agent bruker samme modell. Websøk er aktivert via DuckDuckGo-pluginen, og minnesøk er flyttet over til lokal Ollama-basert embedding for mer robust, lokal semantisk recall.

Modeller

  • Primær agentmodell: microsoft-foundry/gpt-5.4
  • Tilgjengelige agentmodeller: microsoft-foundry/gpt-4o og microsoft-foundry/gpt-5.4
  • Embedding / memory: Ollama med nomic-embed-text

Minne

  • Provider: ollama
  • Modell: nomic-embed-text
  • Fallback: none
  • Status: vektor-/semantisk søk er verifisert som fungerende

Gateway

  • Mode: local
  • Bind: loopback
  • Port: 18789
  • Tailscale: off
  • Auth: token-basert

Tools / plugins

  • Tool-profil: coding
  • Web search: DuckDuckGo aktivert
  • Plugins: duckduckgo, microsoft-foundry
  • Telegram-kanal: aktivert i config

Agenten kan typisk håndtere:

  • list trips
  • show latest trip
  • render latest trip as image
  • render latest trip as link
  • render trip 2026-05-16T11-56-51Z as image
Hvorfor minneoppsettet betyr noe her: OpenClaw-minnet var tidligere skjørt nok til at prosjektkontekst ikke alltid kom tilbake ved behov. Det ble reparert ved å bytte embedding-provider til lokal Ollama, trekke modellen nomic-embed-text, og reindeksere hovedagentens minne. Dermed kan prosjektfakta om Pi, repoer, tjenester og agentoppsett gjenfinnes lokalt uten skyavhengighet.

10. Hvorfor dette oppsettet er smart

  • Pi-en gjør tungt arbeid lokalt der GPS-en faktisk er.
  • Repoene fungerer som ryddige, versjonerte og delbare grensesnitt.
  • OpenClaw-agentene kan lese historikk uten å være tett koblet til live-runtime.
  • GitHub Pages gir en enkel, robust publiseringsflate for interaktive kart.
  • UTC i rådata + lokal tid i presentasjon gir både teknisk orden og menneskelig riktig visning.

11. Nåværende begrensninger

  • Turlogikken er heuristisk og vil fortsatt måtte finjusteres mot reelle kjøreturer.
  • Eksportstrukturen bruker fortsatt flat trips/-mappe.
  • Render-/sync-script ligger i runtime-miljøet på Pi-en og er ikke fullt samlet i ett eget kode-repo.
  • Agentflyten er god, men kan bli enda tydeligere rundt valg mellom bilde, lenke, HTML og GPX.

12. Oppsummert

Hele systemet kan forstås som en kjede: GPS-dongle → Pi/runtime → SQLite → turbygging → eksportrepo → kartrepo → OpenClaw-agenter → chat/visning. Hver del har én tydelig jobb, og de er koblet sammen på en måte som gjør både drift, historikk og presentasjon håndterbar.

Denne siden er lagt i kartrepoet som praktisk systemdokumentasjon, selv om den er bredere enn bare kartpublisering.
